# P1 验证报告（V2.0）：摄像头识别与无声录像

- 报告版本：V2.0 / 2026-11-01
- 对应需求：复检本机摄像头识别、预览、无声录像、取消/重录/释放，并给出本机可复现的命令
- 结论一句话：**摄像头硬件、驱动与系统权限正常，V2.0 的录像链路在“被 Windows 授权访问摄像头的程序”下实测全部通过（7/7），但本机 Windows 对每个可执行文件单独授权，未获授权的 python.exe / EXE 仍会被静默拒绝。**

本报告与早先的《P1 技术可行性验证报告》（音频/笑声路线，已归档到 `docs/archive/`）无关；V2.0 不再使用麦克风或任何音频输入。

## 二、关键发现：本机 Windows 按“程序路径”单独授权摄像头

这是本次复检最重要的结论，也是此前“检测不到摄像头”的真正原因。

1. 隐私开关全部为 `Allow`，设备状态正常，说明不是系统开关或驱动问题。
2. Qt 的两种多媒体后端（默认 `ffmpeg`、`QT_MEDIA_BACKEND=windows`）都返回 **0 个摄像头**，用 DSH 终端、`Shell.Application.ShellExecute` 启动的进程、`Win32_Process.Create` 启动的进程结果一致，排除了执行环境/沙箱因素。
3. 用 Media Foundation 直接探针（`MFCreateDeviceSource`）可以稳定复现差异：
   - `C:\Python311\python.exe`（在 Windows 授权清单里）→ `S_OK`；
   - 项目虚拟环境 `.venv\Scripts\python.exe`、以及把同一个 python.exe 复制到新路径后运行 → `0x80070005 E_ACCESSDENIED`。
4. `HKCU\...\CapabilityAccessManager\ConsentStore\webcam\NonPackaged` 下只有 5 个已获授权的程序：`C:\Python311\python.exe`、旧版 V1.1 的 `NailongQuanxue.exe`、P1 采集探针 `P1CaptureProbe.exe`、`ShellHost.exe`、微信 `Weixin.exe`。
5. WinRT 交叉验证（`MediaCapture.InitializeAsync`）成功、DirectShow（ffmpeg `-list_devices`）能列出 `ASUS FHD webcam`，说明硬件与驱动层完全可用。

也就是说：**换一个未被授权的可执行文件，摄像头就在系统层被拒，Qt 随之枚举为空。** 这不是奶龙劝学的缺陷，但会影响首次使用体验，因此做了两处产品侧处理（见第四节）。

## 三、验证方法（可复现）

新增两个只在本机运行的检查工具，均复用 V2.0 正式代码 `app/camera_recorder.py`（不复制实现、不上传画面）：

```powershell
# 一键看设备、看权限、跑自检（推荐）
powershell -ExecutionPolicy Bypass -File tools\camera_check.ps1

# 只枚举
powershell -ExecutionPolicy Bypass -File tools\camera_check.ps1 -DevicesOnly

# 保留录像以便人工查看（默认删除）
powershell -ExecutionPolicy Bypass -File tools\camera_check.ps1 -Keep

# 打开 Windows 摄像头权限设置页
powershell -ExecutionPolicy Bypass -File tools\camera_check.ps1 -OpenSettings
```

自检脚本 `tools/camera_check.py` 的检查顺序：枚举 → 启动 → 预览帧 → 无声录像落盘 → 取消清理 → 重新录制 → 释放，最后输出 JSON 报告 `build/camera-check.json`（不写入仓库，`.gitignore` 覆盖）。

如果自检报告“没有枚举到摄像头”，应按顺序检查：

1. 设置 → 隐私和安全性 → 摄像头：打开“摄像头访问”和“允许桌面应用访问你的摄像头”；
2. 同一页的应用列表里，把 `python.exe` 或 `NailongQuanxue.exe` 的开关打开（**本机实测：未列出的程序会被静默拒绝**）；
3. 笔记本的摄像头物理开关/热键（如 `Fn+F10`）与 MyASUS 的摄像头开关；
4. 关闭正在占用摄像头的会议软件、相机应用后重试。

## 四、本次为验证而修改的产品代码

| 文件 | 修改 | 原因 |
| --- | --- | --- |
| `app/camera_recorder.py` | 新增 `_discard()`：删除失败时（编码器仍持有文件）按 250 ms 重试，直到成功；`stop()` 前先 `recorder.stop()` 结束编码 | 实测发现“取消录制”时 `unlink()` 会因共享冲突失败，取消后的临时 mp4 会残留到下次启动清理 |
| `app/camera_recorder.py` | 新增 `release()`：释放设备但保留已完成的录像文件 | 供自检/未来“保留录像”场景区分“取消”与“保留” |
| `app/camera_recorder.py` | 无摄像头时的文案增加 Windows 授权指引 | 用户看到的是可操作提示，而不是“没有可用摄像头” |
| `app/surrender_dialog.py` | 对话框关闭时用 `_discard()` 删除未确认的录像 | 同上，避免残留 |
| `tools/camera_check.py`、`tools/camera_check.ps1` | 新增自检工具 | 让用户可自行复现，不必依赖开发环境 |
| `tests/test_camera_recorder.py` | 新增 2 个用例（重试删除、立即删除） | 锁定上面这个真实缺陷 |

## 五、仍未验证（明确边界）

1. **打包 EXE 内**的摄像头授权与录像：EXE 路径不在本机授权清单里，本次没有在 EXE 里跑通录像（需要用户在 Windows 设置里授权该 EXE 一次，或换用已授权程序）。这不是代码问题，但属于未验证项。
2. **动作识别**：无真实付费视觉 API 授权，P1 的“真实正反例识别”仍未验证，只用模拟接口验证了判定链路（见 `TEST_REPORT.md`）。
3. **其他机器/其他摄像头驱动**：本报告只覆盖本机 ASUS FHD webcam + AvStream IR camera。
4. 录像画质与 12 秒默认时长在不同机型上的实际表现，未做多机型测量。

## 六、隐私与数据处置

- 自检全程只在本机读写 `%TEMP%\NailongQuanxue\clips\`，**没有任何画面离开本机**，也没有调用任何视觉 API。
- 本次实测产生的录像已在检查结束后删除；`-Keep` 仅用于用户自行确认，脚本会打印保留路径。
- 应用本身仍然只把“抽帧后的少量静止画面”发到用户自己填写的 Base URL（见 `PRIVACY.md`），原录像只保存在本机。
